# AGENTS.md — QR-Based Attendance System

FastAPI backend (18 feature slices, 21 models, 17 Alembic migrations) + SvelteKit 2 / Svelte 5 frontend. Real API by default, mock opt-in via `PUBLIC_MOCK_MODE`. No linters or formatters; CI runs the backend suite, `alembic check`, and the frontend typecheck (ADR-069). `README.md` is current; when docs conflict, trust `README.md` + executable config.

## Backend

- Entry `src/main.py`: `/health`, CORS, lifespan `SELECT 1` on boot — **fails to boot if DB unreachable**. The lifespan also starts/stops the cron scheduler. Only `AppException` has a handler; `DomainException` → 422, `DatabaseException` → 409.
- Config `src/core/config.py`: pydantic-settings, `get_settings()` cached. `JWT_SECRET` required when `DEBUG=false`. `RECOVERY_TOKEN_EXPIRE_MINUTES` defaults to 5 in code and in `backend/.env.example`.
- Scheduler: `src/core/scheduler.py` owns the APScheduler lifecycle (`get_scheduler()`, `BackgroundScheduler`) and imports nothing from `features`/`shared`. Job bodies are adapters in their own feature — `analytics/batch.py::run_scheduled_risk_batch`, `system/service.py::run_scheduled_backup` — and each **commits its own transaction**, because the services only `flush()` and `_get_db` is request-only. Crons: `RISK_BATCH_CRON` (02:00), `BACKUP_CRON` (03:00), both overridable via `SCHEDULER_ENABLED`/`_TIMEZONE`/`_MISFIRE_GRACE_SECONDS`. See ADR-063.
- Deps `src/api/deps.py`: use `_get_db` (no public `get_db`), `_get_current_user` / `_get_optional_current_user`, `require_role(*roles)` (`super_admin` passes `admin` checks), `*ServiceDep` annotated service deps. `_get_db` commits on success, rolls back on any exception.
- Routers: `src/api/router.py` mounts under `/api` with **no `prefix=` arg — each `APIRouter` bakes its own prefix in**. One router per (feature, mount point); never mount the same router twice. `enrollment/router.py` is a stub and stays **unmounted**. Currently **23 routers over 15 mount paths** (24 `*router*.py` files exist; the unmounted one is `enrollment`). `/api/admin/dashboard` is a route on the `/admin` mount (`dashboard/admin_router.py` uses `prefix="/admin"` with inner `@router.get("/dashboard")`), not a separate mount. `face_enrollment/router.py` (mounted at `/admin/face-enrollment`) exposes `GET` status, `POST` enroll (multipart), and `DELETE` revoke.
  - `/api/professor` is shared by **five** routers: `session/router.py` owns courses/sessions/attendance; `professor/router.py` owns `profile*` only; `excuse/professor_router.py`, `reports/router.py`, `dashboard/professor_router.py` own their own subtrees. Don't cross them.
  - `/api/student` is shared by **four** routers: `student/router.py` (verify-code, face-embedding, schedule, profile), `attendance/router.py` (scan, precheck, history), `excuse/student_router.py`, `dashboard/student_router.py`. Inner paths must not collide.
  - `/api/admin` is shared by `system/router.py` (audit-logs, system settings, academic-structure) and `dashboard/admin_router.py` (`/dashboard`).
  - `course/` has two routers (`router.py` → `/admin/courses`, `offering_router.py` → `/admin/offerings`); `student/` and `professor/` each add an `admin_router.py` for their roster CRUD.
  - Collection routes use `@router.get("")`, not `"/"` (trailing-slash redirect breaks the contract).
- Services: admin CRUD slices (`program`, `course`, `student`, `professor`) are `class <Feature>Service` with one `BaseCRUD` per model via `<Feature>ServiceDep` (ADR-058). `SessionService` and `FaceEnrollmentService` are also classes. Everything else stays module-level functions (ADR-055). Face enrollment runs six biometric quality gates via `shared/face_quality.py::assess_image_bytes` (MediaPipe FaceLandmarker) before embedding generation; `FaceEnrollmentService` raises `InvalidImageException`/`NoFaceDetectedException`/`MultipleFacesException`/`QualityTooLowException`. Embeddings are generated server-side via `shared/face_embedding_generator.py` (MobileFaceNet ONNX, 512-d, with landmark fallback); content-type is not trusted.
- Alembic: head is `b9c0d1e2f3a4` (20 revisions; the latest adds the session open-window columns — `actual_start_time`, `original_scheduled_start_time`, `override_reason`, `created_by`). New model → add `import features.X.model` to `alembic/env.py`, `alembic revision --autogenerate`, `alembic upgrade head`. `alembic check` must say "No new upgrade operations detected".
- **`alembic check` is the only guard against migration drift, and CI runs it** (`.github/workflows/ci.yml`, job `migrations`, against a `postgres:16-alpine` service — ADR-069). `conftest.py` builds the test schema with `Base.metadata.create_all`, straight from the models, so the suite never exercises the migration chain and cannot detect drift in either direction — a test asserting a unique column passes against both schemas. When an applied migration disagrees with a model, **fix the migration, never the model** (ADR-065): never edit an already-applied revision, add a forward migration. A failing `migrations` job means drift, not a flaky check.
- Models (21 classes, 13 files; `admin`, `dashboard`, `face_enrollment`, `reports`, `upload` model-less): `Student.user_id` / `Professor.user_id` are unique FKs to `users.id` (1:1). Deletes use `ondelete=RESTRICT` — archive routes need a has-records guard (409); never relax to CASCADE. `DELETE /admin/programs/{id}` flips `programs.is_active` only; there is nothing to cascade to (no `is_active` on year levels, no program FK on courses). Archive/reactivate/hard-delete sync `users.is_active` (D71); re-creation reclaims an inactive login via fresh CLAIM OTP (D72). `users.username` is removed — do not re-add; register/admin-create 409s are email-only (D73). Newest tables/columns are `course/model.py::OfferingComponent` and `sessions.session_type` (D77): lecture/lab is persisted per session, and each offering carries one scheduled component per type. Professor assignments are effective-dated on `(offering_id, professor_id, effective_from)`; never mutate that composite key. At most one **primary** assignment may overlap an offering on any date; assistants may overlap, and adjacent primary ranges are valid. `assign`, `reassign`, and `reopen` all enforce this with `409 primary_assignment_conflict` (reopen accepts `is_primary=false` to restore a former primary as an assistant). End sets `effective_to = today` (future rows are deleted), reassign closes the old row and creates the new one, and reopen clears `effective_to` only when no later row exists; all three audit through `course_professor`.
- Weekly hours are **one** rule: `shared/schedule.py` (`distinct_day_count`, `meeting_minutes`) is the single definition, and course `units × 60` is an *exact* requirement for an offering's merged active-component total (D79). Enforced on offering/component writes (`weekly_hours_exceed_units` / `weekly_hours_below_units`, both 422), on offering activation (`schedule_mismatch`, D82, names the course and hours), and on session open (`offering_schedule_mismatch`, 422; rows with no configured meetings are exempt); `ProfessorService` derives the `schedule_ok` flag from the same math. Like `rates.py`, do not re-derive it per feature.
- Auth quirks: forgot-password step 2 returns a 5-min `type="recovery"` grant required to mint the OTP; unknown emails get a deterministic decoy question (ADR-056). `users.security_question_hash` stores the question in plaintext under a legacy name — only the answer is hashed; don't "fix" without revisiting the contract. Login OTP has two fixed-window limiters in `auth/service.py`: per-email `_login_otp_limiter` (3 wrong codes) and per-IP `_login_otp_ip_limiter` (15) — the split is ADR-074; resend resets the email budget.
- Dashboard slice (`features/dashboard/`): three routers, three mount points, so `api/router.py` includes it **three times** — `dashboard_student_router` (`/student/dashboard`), `dashboard_professor_router` (`/professor/dashboard`), `dashboard_admin_router` (`/admin` mount, `/dashboard` route). One router per (feature, mount point); never add a fourth. It aggregates features it doesn't own, so every figure is **composed from an existing service method** rather than recomputed — `compliance_rate` is `get_history().summary.compliance_rate`, admin `avg_rate` is `AnalyticsService.get_overview().avg_compliance_rate` (compliance, NOT participation), and `pending_sync` calls `SystemService.pending_sync_total` **directly** because `get_system_settings()` INSERTs missing `AppSetting` rows — a GET must not write. Roster counts (`student_count`/`professor_count`/`program_count`) count active `is_active` rows and are deliberately *not* the analytics overview's `total_students` (which counts enrolled-in-scope). "Today" means **UTC** throughout. `schedule_days` letters are interpreted by `student/service.py::_meets_on` — `T`=Tuesday, `H`=Thursday, `U`=Sunday — test it as a pure function; `Session.created_at` is the column session queries filter on, not `scheduled_start_time`.
- Analytics filter scope: the admin rail's Courses control reads `GET /admin/analytics/course-options`, derived from the same `_offerings_stmt` predicate every analytics read uses — never list the catalogue in the picker (a course with no offering in scope can never produce a row, so offering it yields a silently empty report). `course_ids` is honored by overview/comparison/trends/at-risk/staging **and** by `risk-staging/promote` along with program/year; promote is no longer semester-only. See ADR-085 (#279).
- Password resets: `AuthService.admin_reset_password` is the **single** implementation behind all three admin routes (`/admin/{users,students,professors}/{id}/reset-password`). The student/professor routers resolve the roster row to a `users.id` first (`StudentService.account_user_id` / `ProfessorService.account_user_id`, 409 `*_account_unlinked` when there is none) and then call it — so a credential write has one home, not three. An admin reset also clears `failed_login_attempts`/`is_locked`/`locked_at` (an admin rescuing a locked-out account needs it) and sets `performed_by` to the admin while `entity_id` stays the account. It must **not** touch MFA — that is `disable_mfa`'s job, password-verified. Two service deps on one route is the `reports/router.py:47` pattern.
- MFA is a two-writer field: `verify_mfa` is the only place that sets `mfa_enabled = True` (setup alone writes the secret and leaves the flag False), and `disable_mfa` (`POST /auth/mfa/disable`) is the only path back to False. Any new MFA write site must invalidate unconsumed backup codes the same way — `disable_mfa` stamps `used_at` rather than deleting, which is what makes `list_backup_codes` report 0. Disabling cannot revoke issued refresh tokens (stateless JWTs, no revocation list); that limitation is written up in `security-model.md` T6 / Password & Account Security.
- Email: `shared/email.py` is the one delivery path — real `smtplib`, stdlib only, and it **never raises** (`debug` logs, empty `SMTP_HOST` logs+skips, otherwise implicit TLS 465 / STARTTLS 587). `SMTP_*` in `core/config.py` is deliberately unvalidated (unlike `JWT_SECRET`) so a deployment without a relay still boots. `send_otp_email` keeps its old signature because `auth/service.py` calls it inline; new code that must not block uses `dispatch_emails` (one executor job per batch, futures parked in `shared.email._PENDING`). Excuse notifications: copy in `features/excuse/notifications.py` (pure builders), recipient resolution + dispatch in `ExcuseService`, always last in the method so a raise sends nothing. Recipients read `users.email` first, then the profile's roster `email`. Only §8's four events notify — `quick_excuse`/`excuse_with_evidence`/`edit_excuse`/`revoke_excuse` are silent, and the in-app half is unimplemented (no table, by design).
- Audit: `shared/audit.py::record_audit` is the ONE writer — flush-only, so a row rolls back with the mutation it describes. `action`/`entity_type` are typed by `shared/enums.py::AuditAction`/`AuditEntity` (free-form columns, no DB constraint, **no index on `action`**). Read via `GET /admin/audit-logs` (all rows, 4 filters); `GET /admin/system/academic-structure` reads the same table scoped to the 4 structural entity types. Both live in `system/router.py` (prefix `/admin`); `AuditFilterInvalidException`/`AuditDateRangeInvalidException` are 422. One exception to "services only flush": lockout bookkeeping in `auth/service.py` commits on its own session (`_lockout_transaction`) because the request that raises 400 would otherwise roll the counter back — see ADR-064.

**Attendance review band**: `_decide_scan_outcome` stores the computed status (`PRESENT`/`LATE`) as `validation_status` for review-band face matches (`review_low <= score < threshold`), keeping the computed value in `original_status` for admin review restoration. `_pending_review_filter` keys on `cast(liveness_evidence["review"], Boolean) == True` (not `validation_status == PENDING`), and `_load_pending_review` gates on `evidence.review` only. This means review-band records read as `present`/`late` on student history and professor pages while still appearing in the admin review queue via `evidence.review == true`.
- Scan flow (D27, rejection reasons D15): `POST /student/attendance/{scan,precheck}` resolve the student from the **authenticated user**, only *comparing* `payload.student_number` case-insensitively → `403 student_number_mismatch`. Same rule applies to any new student-facing endpoint taking an ID (e.g. excuse submit). The student-ID QR scan is **not** part of the flow and must not be reintroduced: the SPA's only QR step scans the session code (`QRScanner.svelte`), and the ID step is the typed/prefilled confirmation above. Idempotency key is `user_id:session_id:X-Idempotency-Key`, 15-min TTL, process-local (like `rate_limit` — needs a shared store for multi-instance). **Sync replays**: `submit_scan` passes `allow_expired=True` to `_get_active_session`/`_resolve_scan_parties` when an `X-Idempotency-Key` is present, so a queued scan can still be recorded after the session's `expires_at` has passed.
- Session scheduling (D93/D94/D96): a session may be opened only while its class is running (open window); an explicit override is the way past it. `expires_at = min(max(scheduled_start_time, created_at) + duration, scheduled_end_time)` so a session opened for a future class is not born expired and is not scannable until `scheduled_start_time` (`SessionNotStartedException` / `session_not_started`, 422). Status is derived as `scheduled`/`active`/`closed` (no status column). Override start times may not point into the past (`OVERRIDE_PAST_GRACE_MINUTES = 0` → `scheduled_start_in_past`, 422). Duration is capped by the meeting window (non-override ≤ `plan.meeting_minutes`; override ≤ remaining window) → `invalid_session_time`. Institution timezone is `INSTITUTION_TIMEZONE` (default UTC; tests assume UTC).

**Professor active-session student tiles** (`SessionService._active_student_items`): unscanned students read as `pending` while the session is `scheduled`/`active`, and `absent` once `closed`. Scanned students keep their server-decided status (`present`/`late`). The session status is passed as a parameter — one computed value drives both the response `status` field and the default tile status.
- Benchmark profile (Phase 9, see ADR-067): `BENCHMARK_MODE=true` skips the scan geofence + liveness checks (`attendance/service.py`) and the per-IP scan rate gate (`attendance/router.py`); `RISK_BATCH_WORKERS` shards risk scoring across threads order-preservingly (`analytics/batch.py`). Both default off, so production behavior is unchanged; `test_scan_validation.py` and `test_risk_batch.py` cover each.
- Load-harness traps (Phase 9): never import `locustfile` from the suite — importing locust pulls in gevent monkey-patching and hangs pytest, which is why the harness's helpers live in `bench_timings.py` and why `test_locust_discovery.py` asserts on `locustfile.py`'s *source text* rather than calling it; locust calls `wait_time` bound, so the callable must accept the user argument; a virtual user's identity must come from `SlotAssigner`, never `id(user) % pool` (CPython's aligned addresses collapse onto a few residues and the users then rescan each other's sessions).
- Load gate: `locustfile.py::_report` asserts §2's targets (scan rps, p95, p99, 0 duplicates, slowest replay batch) and sets `environment.process_exit_code = 1` on a miss, so a load run is CI-gateable; thresholds are `LOCUST_MIN_RPS` / `LOCUST_MAX_P95_MS` / `LOCUST_MAX_P99_MS` / `LOCUST_MAX_DRAIN_S`, and the gate only ever forces failure (a clean run leaves the exit code to locust's own `exit_code_on-error`). Throughput counts successful scans over the wall-clock window, not `stats.total.total_time` (that is a sum of response times) nor `total_rps` (that is blended across login/profile/scan). `get_current_response_time_percentile` returns `None` when its trailing-10s cache has no samples — coerce it to a pass and a short run gates green.
- Load queue: slots 1-15 scan live, 16-25 backlog 1-3 scans, 26-30 backlog 5-8 (`_profile_for_slot`); a queued scan is a real POST with `scanned_at` now minus `LOCUST_QUEUE_STALE_S` (default 90, must stay above the 60s staleness floor or replays stop writing sync rows). Each user tracks live-scanned vs backlogged sessions in disjoint sets, because the second scan for a (student, session) is a 409 `duplicate_scan` that fails the gate; leftover backlog replays in `on_stop`. Replayed scans count toward `scans_ok` and carry fresh `X-Idempotency-Key` values — a reused key returns the prior result instead of queueing, which would make the drain leg vacuous.

## Backend tests

- `api_client` commits only on success, so a **failing request rolls back the seed** — commit after seeding if a test issues two failing requests. Read `server_default` values before committing (else `MissingGreenlet`).
- Autouse fixture clears process-global caches: `attendance.service._IDEMPOTENCY_STORE`, `rate_limit._limiter._windows`, `auth.service._recovery_limiter._windows`, `auth.service._login_otp_limiter._windows`, `auth.service._login_otp_ip_limiter._windows`, `shared.cache._cache._store`, `shared.email._PENDING`, `face_quality._landmarker` / `_landmarker_failed`, `face_embedding_generator._onnx_session` / `_onnx_failed`, plus the scheduler (`core.scheduler.reset_scheduler()`, which clears `_IN_FLIGHT` and unbinds the singleton). Add any new module-level cache here.

## Frontend

- **No service hard-codes `MOCK = true`** — `client.ts:18` is the only reader of `PUBLIC_MOCK_MODE`, and every service branches on `isMockMode()`. Several still hold a local fixture fallback for the mock leg (in `excuse/mock.ts`, `report/mock.ts`, the `sync` in-memory queue, the `MOCK_*` consts in `api/endpoints.ts`) — that is a data fallback, not a pinned flag. - Student scan page (`src/routes/student/scan/+page.svelte`) maps backend scan error codes via `SCAN_ERROR_MESSAGES` (incl. `stub_embedding`) and `toUserMessage()` returns a safe fallback for unmapped `APIError`s; the client-side geofence failure throws `APIError('outside_geofence', …)` so it uses mapped handling, and a `result.status === 'rejected'` scan shows "This session is no longer accepting attendance." (no raw backend messages leak).
- Professor session creation page (`src/routes/professor/sessions/create/+page.svelte`) shows a confirmation panel after a successful `openSession()` and only navigates to `/professor/sessions/active/{sessionId}` when the professor confirms it; no navigation on validation/server/network errors or missing ID. The `Generate Session Code` button also asks once more before opening the session, restating course, type, scheduled time and duration (D96).
- The `session_already_active` 409 now names the course and the active session's scheduled window (`CS101 2026-10-26 08:03–09:03`) rather than the offering id; `SessionService._require_no_active_session` returns the active `Session` row and resolves the course code via the offering's `course_id` (D96).
- Professor active-session page (`src/routes/professor/sessions/active/[id]/+page.svelte`) reflects authoritative session lifecycle: header label reads "Scheduled:" / "Closed:" / "Active:" from `session.status` (not the URL); a future-start session shows "Scheduled" with a "Class starts in" countdown to `scheduledStartTime`; tick interval freezes only when `session.status === 'closed'`; `classRemainingSeconds` returns 0 when closed or scheduled; the class-end timer shows `expires_at` (falls back to `scheduledEndTime`) as the actual end time when closed instead of a running countdown; the skeleton gate no longer blocks on `classRemainingSeconds === null`. Backend `SessionActiveResponse` carries `scheduled_start_time` + `expires_at` (nullable); scan rejection on closed sessions is enforced by `AttendanceService._get_active_session` (expires_at <= now → `SessionExpiredException`), and on not-yet-started sessions (now < scheduled_start_time → `SessionNotStartedException` / `session_not_started`). No migration needed — `scheduled_start_time` and `expires_at` already exist on the `sessions` table. Session status is now derived as `scheduled`/`active`/`closed` (no status column).
- Face enrollment confirmation: clicking "Upload enrollment" / "Remove enrollment" in the admin student modal opens a **sibling confirmation overlay** (`faceConfirm` = `'save'`/`'remove'`) at `z-index: 120`, outside the outer modal `<div>`. While `faceConfirm` is set, the outer modal's `trapFocus` is destroyed (`use:trapFocus={faceConfirm ? undefined : { onEscape: () => closeFace() }}`) so only the overlay's `trapFocus` is active — this prevents the two `document`-level `focusin` listeners from fighting and causing a stack overflow (the prior `onEscape: () => (faceConfirm ? undefined : closeFace())` kept the outer action alive while the overlay mounted). On success `performUploadFace`/`performRevokeFace` set `faceConfirm = null` and call `clearFacePhotos()`; the outer `trapFocus` re-applies on close.
- Face enrollment camera (`FaceEnrollmentCamera.svelte`): after each capture a review panel shows ("Use Photo" / "Retake Photo"). "Use Photo" commits the file and advances (front→left→right→complete), disabling `autoCapture` and restarting the stream for the next angle while preserving the front yaw baseline. "Retake Photo" restarts the stream cleanly (`stop()` + `start(true)`, preserving step/yaw baseline) and resets `autoCapture` to `false`. An "Automatically capture when aligned" checkbox gates auto-capture.
